# Практическая работа №13

Три независимых приложения на Go 1.26 / Gin. У каждого собственный Go-модуль,
Dockerfile, домен, бизнес-слой и PostgreSQL-репозиторий. Общего Go-кода между
сервисами нет. PostgreSQL 17 работает в одном контейнере: БД и роли `users`,
`orders`, `notifications` изолированы. Взаимодействие приложений — только HTTP.

## Запуск

Из корня проекта:

```sh
docker compose up -d --build
docker compose ps
```

API: User — `http://localhost:8081`, Order — `http://localhost:8082`,
Notification — `http://localhost:8083`. В сети Compose приложения обращаются
по DNS-именам `user-service` и `notification-service`, внутренний порт 8080.
БД наружу не опубликована. Пароли в Compose предназначены для локальной работы.

```sh
docker compose stop notification-service
docker compose start notification-service
docker compose stop user-service
docker compose start user-service
docker compose logs notification-service
docker compose down
```

Инициализация схем выполняется при первом создании тома PostgreSQL.
`docker compose down` сохраняет данные. `docker compose down -v` удаляет данные
и позволяет заново выполнить инициализацию (использовать только при необходимости).

## API

Тело POST и PUT передаётся в JSON с заголовком `Content-Type: application/json`.
Ответы: `{"data": ...}` или `{"error": "..."}`. UUID создаёт сервер.
Создание — 201, чтение/замена/удаление — 200, неверные поля — 400,
отсутствующая сущность — 404. PUT заменяет все изменяемые поля.

| Сервис | Ресурс | Поля POST и PUT |
|---|---|---|
| User (8081) | `/api/v1/users` | `{"name":"Илья","email":"ilya@example.com"}` |
| Order (8082) | `/api/v1/orders` | `{"user_id":"<UUID пользователя>","product":"Книга","quantity":2}` |
| Notification (8083) | `/api/v1/notifications` | `{"user_id":"<UUID пользователя>","message":"Заказ принят"}` |

Для каждого ресурса доступны:

- `POST <ресурс>` — создание;
- `GET <ресурс>` — список;
- `GET <ресурс>/<UUID>` — получение;
- `PUT <ресурс>/<UUID>` — замена;
- `DELETE <ресурс>/<UUID>` — удаление.

При создании заказа Order Service проверяет пользователя по HTTP, сохраняет
заказ в своей БД и отправляет HTTP-запрос в Notification Service. Сервис
уведомлений сохраняет сообщение и выводит его в лог как заглушку отправки.
Недоступность Notification Service не отменяет заказ: ответ имеет статус 201
и `notification_sent: false`. Недоступность User Service возвращает 503 без
создания заказа; отсутствующий пользователь — 400.

`notification_sent` присутствует только в ответе POST заказа и отражает результат
единственной HTTP-попытки в рамках запроса. Флаг не хранится в БД. При сетевом
сбое после сохранения уведомления результат доставки может быть неопределённым.
Автоматических повторов и восстановления пропущенных уведомлений нет.
Изменение заказа не отправляет новое уведомление. Пользователь проверяется
при POST и PUT заказа. Notification Service принимает самостоятельные сообщения,
не проверяя User Service. Межсервисных внешних ключей и каскадного удаления нет:
удаление пользователя сохраняет историю заказов и уведомлений.

HTTP-клиент Order Service имеет таймаут 3 секунды. Обработка ошибок сети нужна
для обязательного сценария отказа; retry, circuit breaker и мониторинг не добавлены.
Логирование реализовано через zap.

## Конфигурация

Все настройки читаются из окружения. Общие: `SERVER_PORT` (по умолчанию `:8080`),
`LOGGER_LEVEL` (`info`), `POSTGRES_HOST` (`localhost`), `POSTGRES_PORT` (`5432`),
`POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` (по умолчанию имя домена
`users`/`orders`/`notifications`, пароль `<домен>_local`).
Для Order: `USER_SERVICE_URL` и `NOTIFICATION_SERVICE_URL`.
DSN формируется методом конфигурации. Подключение БД — pgxpool, SQL — squirrel.

## Проверки

В каждой папке сервиса: `go test -race ./...` и `go vet ./...`.
Unit-тесты Order Service проверяют ошибки зависимостей, порядок сохранения и
отправки, ответы HTTP-клиента, неверный JSON, сетевой отказ и отмену контекста.

После запуска системы из корня проекта:

```sh
python3 tests/integration.py
```

Тест использует реальные HTTP и PostgreSQL: CRUD всех сервисов, валидацию,
уведомление о заказе, отключение обоих зависимых сервисов, сохранность данных
при рестартах приложений и запрет доступа ролей к чужим БД. Он временно
останавливает сервисы и удаляет созданные им записи после проверки.
